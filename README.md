# Algorithm Grand Prix

Algorithm Grand Prix is a four-player pathfinding race for BFS, DFS, Dijkstra and A*. The main screen runs the shared maze visualization and up to four phones join the same round.

## How the deployment works

The browser pages are static and the multiplayer state is handled by small HTTP requests. On local Node.js, the server can use in-memory state. On Vercel, the roster, maze, round and race results are stored in shared Upstash Redis so separate serverless function instances see the same game.

The app deliberately does **not** write runtime log files.

## URLs

- `/` — SEO landing page
- `/screen` — main projector/screen
- `/controller` — mobile player controller
- `/join` — redirects to the mobile controller

The old `/screen.html` and `/controller.html` addresses redirect to the clean routes.

## QR code

The QR code is generated by the server from the request host/protocol, so it does not contain a hardcoded Vercel domain.

- On Vercel or another public host, it points to that exact site's `/controller` route with a `?join=new` flag so a QR scan creates a fresh player session.
- On local Node.js, when the screen is opened through `localhost`, it uses the PC's LAN address instead so phones on the same Wi-Fi can scan and join. The controller releases the phone's previous waiting session before creating a fresh QR session, preventing stale Player 2 assignments.

## Fresh Vercel deployment

1. Extract this project and push the whole folder to a fresh GitHub repository.
2. In Vercel, import that repository and deploy the project root.
3. Create/connect an **Upstash Redis** database through the Vercel integration.
4. In the Vercel project environment variables, confirm these exist for the environment you will deploy:

   `UPSTASH_REDIS_REST_URL`

   `UPSTASH_REDIS_REST_TOKEN`

   The server also accepts `KV_REST_API_URL` and `KV_REST_API_TOKEN` for compatible existing integrations.

5. Redeploy after the Redis variables are available.
6. Open the production site's `/screen` URL on the projector/PC.
7. Scan the QR from up to four phones. Each phone should receive a stable player number and share the same player state with the screen. The saved name is sent during the initial join request, so the controller should not need a second round-trip just to save the name.

The shared-state key includes the Vercel deployment ID, so a fresh deployment starts with a fresh multiplayer state instead of inheriting players from an older broken deployment.

## Vercel sanity check

Open the following on the deployed domain:

`/api/health`

A working multiplayer deployment should return JSON with:

- `ok: true`
- `sharedState: true`
- `realtime: "shared-http-polling"`

When Redis is missing, the API returns a clear `SHARED_STATE_REQUIRED` response instead of leaving the player page stuck in a misleading connection state.

## Final stability update

This build includes:

- Fresh player sessions from `/controller?join=new` so multiple controllers do not reuse Player 1 in the same browser.
- The landing page explicitly offers **OPEN MAIN SCREEN** and **JOIN AS NEW PLAYER**.
- The screen QR fallback also uses a fresh-player URL.
- Faster shared-state polling: about 400 ms for the screen and 550 ms for controllers.
- Immediate player/screen leave signaling with `navigator.sendBeacon` plus a `keepalive` fetch fallback when a page closes or navigates away.
- A shorter stale-session fallback TTL (12 seconds) for cases where the browser cannot send a leave signal.
- Existing CSS, maze rendering, algorithms, Redis shared state, round handling, and safety checks are preserved.

For Vercel, connect Upstash Redis to the project and redeploy after changing environment variables.
